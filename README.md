## بخش ۱ — چگونه می‌توان یک سرویس را فقط روی شبکه داخلی اجرا کرد؟

برای داخلی نگه داشتن سرویس، باید دسترسی شبکه به آن محدود شود؛ صرف انتخاب یک شماره پورت غیرمعمول یا مخفی کردن نشانی، کنترل دسترسی محسوب نمی‌شود. روش مناسب به محل اجرای پروکسی و سرویس بستگی دارد:

۱. **اجرا روی یک میزبان:** اگر پروکسی و سرویس هر دو مستقیماً روی یک سیستم اجرا شوند، سرویس را به `127.0.0.1:8081` متصل می‌کنیم. در این حالت فقط برنامه‌های همان میزبان می‌توانند به آن متصل شوند. برای go-httpbin دستور زیر قابل استفاده است:

```bash
go run github.com/mccutchen/go-httpbin/v2/cmd/go-httpbin@v2.19.0 -host 127.0.0.1 -port 8081
```

۲. **اجرا روی میزبان‌های جدا:** سرویس را فقط به IP خصوصی کارت شبکه داخلی متصل می‌کنیم و با فایروال، پورت ۸۰۸۱ را فقط برای IP پروکسی و کاربران مجاز داخلی باز می‌گذاریم. روی روتر نیز نباید برای آن پورت Port Forwarding تعریف شود. داشتن IP خصوصی به‌تنهایی جای فایروال و جداسازی مسیرهای دسترسی را نمی‌گیرد.

۳. **روش پیاده‌شده در این پروژه:** کانتینر `legacy` فقط عضو شبکه Docker به نام `backend` است. این شبکه با `internal: true` تعریف شده و برای سرویس legacy هیچ `ports` تعریف نشده است. پروکسی به شبکه داخلی و شبکه ورودی متصل است و فقط پورت ۸۰ میزبان برای آن منتشر می‌شود. بنابراین کاربر بیرونی به پورت منتشرشده legacy دسترسی ندارد و باید از پروکسی عبور کند.

```yaml
legacy:
  environment:
    HOST: 0.0.0.0
    PORT: "8081"
  expose:
    - "8081"
  networks:
    - backend
```

در اینجا `0.0.0.0` مربوط به فضای شبکه خود کانتینر است. استفاده از `127.0.0.1` داخل کانتینر legacy، اتصال پروکسیِ کانتینر دیگر را نیز مسدود می‌کند. `expose` پورت را روی میزبان منتشر نمی‌کند و به‌تنهایی نقش فایروال ندارد؛ جداسازی با عضویت شبکه، داخلی بودن آن و نداشتن `ports` انجام می‌شود. مدیر میزبان و کانتینرهای دیگری که عمداً به شبکه backend متصل شوند همچنان می‌توانند به legacy دسترسی داشته باشند؛ این طراحی برای جلوگیری از دسترسی مستقیم کاربران شبکه خارجی است.

## بخش ۲ — فلسفه TLS Termination چیست؟

در TLS Termination، اتصال HTTPS کاربر در پروکسی ورودی خاتمه پیدا می‌کند. پروکسی گواهی سرور و کلید خصوصی را نگهداری می‌کند، TLS handshake را انجام می‌دهد، داده را رمزگشایی می‌کند و پس از بررسی درخواست، آن را به سرویس داخلی می‌فرستد. بنابراین سرویس قدیمی لازم نیست مدیریت گواهی، تمدید گواهی، الگوریتم‌های رمزنگاری و تنظیمات HTTPS را پیاده‌سازی کند. این وظایف در یک نقطه متمرکز می‌شوند و به‌روزرسانی آن‌ها ساده‌تر است.

مسیر ارتباط در این روش چنین است:

کاربر از طریق HTTPS روی پورت ۴۴۳ به پروکسی متصل می‌شود؛ پروکسی پس از خاتمه TLS، درخواست را از طریق HTTP روی پورت ۸۰۸۱ به سرویس قدیمی می‌فرستد.

TLS و JWT دو نیاز متفاوت را پوشش می‌دهند: TLS محرمانگی و تمامیت ارتباط و احراز هویت سرور را فراهم می‌کند؛ JWT به پروکسی امکان می‌دهد اعتبار مجوز ارائه‌شده را بررسی کند. JWT امضاشده الزاماً رمز‌شده نیست و بخش payload آن قابل خواندن است. همچنین Bearer Token در صورت سرقت، تا زمان انقضا قابل استفاده مجدد است؛ پس ارسال آن روی HTTPS ضروری است.

اگر بخش داخلی روی یک میزبان یا شبکه قابل اعتماد و ایزوله باشد، ارسال HTTP از پروکسی به legacy می‌تواند مطابق مدل تهدید پذیرفته شود. اگر شبکه داخلی نیز قابل اعتماد نباشد، ارتباط دوم را هم با TLS و در صورت نیاز mTLS محافظت می‌کنیم؛ این حالت معمولاً TLS Re-encryption نامیده می‌شود. TLS Termination به‌خودی‌خود ارتباط دوم را رمزگذاری نمی‌کند.

در پیاده‌سازی این تمرین، مطابق درخواست صورت سؤال، ورودی پورت **۸۰** است. فعال‌سازی HTTPS جزو پیاده‌سازی الزامی بخش ۳ نیست و توضیح TLS در این بخش ارائه شده است. برای انتشار واقعی، ورودی HTTPS روی ۴۴۳ و هدایت درخواست‌های HTTP به HTTPS لازم است؛ توکن واقعی نباید روی HTTP عمومی ارسال شود.

## بخش ۳ — پیاده‌سازی JWT Authentication Proxy (۱۰ نمره)

### معماری و انطباق با تمرین

| مؤلفه | پیاده‌سازی |
|---|---|
| سرویس قدیمی | `ghcr.io/mccutchen/go-httpbin:2.19.0` بدون تغییر سورس |
| پورت داخلی | `legacy:8081`، فقط در شبکه backend |
| ورودی خارجی | پورت `80` میزبان که به `8000` کانتینر پروکسی متصل است |
| پروکسی | Python و aiohttp، با بررسی JWT پیش از هر درخواست |
| احراز هویت | هدر `Authorization: Bearer <JWT>` با امضای HS256 |
| صدور توکن | ابزار مدیریتی آفلاین؛ بدون endpoint عمومی صدور توکن |
| پاسخ نامعتبر | `401 Unauthorized` و هدر `WWW-Authenticate` |
| خطای سرویس مقصد | `502` برای خطای اتصال و `504` برای پایان مهلت |

پروکسی پس از تأیید توکن، درخواست را فقط به upstream ثابت می‌فرستد. متد، مسیر خام، query string، بدنه، status code و هدرهای مجاز پاسخ حفظ می‌شوند. Redirect در سمت پروکسی دنبال نمی‌شود؛ پاسخ ۳۰۲ به کاربر بازگردانده می‌شود. هدرهای hop-by-hop عبور نمی‌کنند. توکن از درخواست ارسالی به legacy حذف می‌شود، زیرا httpbin هدرهای ورودی را در بعضی پاسخ‌ها بازتاب می‌دهد. هدرهای هویت و forwarding ارسالی کاربر حذف یا بازنویسی می‌شوند تا هویت جعلی به سرویس منتقل نشود.

همه مسیرها، از جمله `/` و درخواست‌های `OPTIONS`، به JWT نیاز دارند. هیچ مسیر آزاد برای دور زدن احراز هویت تعریف نشده است. انتقال HTTP معمولی و پاسخ‌های جریانی پشتیبانی می‌شود؛ تونل CONNECT و ارتقای WebSocket جزو دامنه این پیاده‌سازی نیستند. سقف بدنه درخواست یک MiB و مهلت upstream سی ثانیه است.


### اعتبارسنجی JWT

JWT از سه بخش base64url با جداکننده نقطه تشکیل می‌شود: header، payload و signature. امضای این پروژه HMAC-SHA256 روی دو بخش اول است. امضای دریافت‌شده با `hmac.compare_digest` مقایسه می‌شود. کلید حداقل ۳۲ بایت است و باید تصادفی تولید شود؛ صرف طولانی بودن یک عبارت قابل حدس کافی نیست.

در این پروژه فقط header استاندارد `{"alg":"HS256","typ":"JWT"}` پذیرفته می‌شود. انتخاب الگوریتم از تنظیمات ثابت کد می‌آید، نه از اعتماد به ادعای توکن. `alg=none`، الگوریتم دیگر، header اضافه، امضای نادرست و JSON دارای کلید تکراری رد می‌شوند. این یک پروفایل محدود برای تمرین است و همه انواع JWT را پیاده‌سازی نمی‌کند.

هر شش claim زیر الزامی‌اند:

| claim | کنترل انجام‌شده |
|---|---|
| `iss` | دقیقاً برابر `http-hands-on` |
| `aud` | دقیقاً برابر `legacy-service` |
| `sub` | رشته غیرخالی؛ شناسه کاربر |
| `iat` | زمان صدور صحیح و بدون تاریخ آینده |
| `nbf` | زمان شروع اعتبار؛ توکن هنوز فعال‌نشده رد می‌شود |
| `exp` | زمان پایان اعتبار؛ توکن منقضی رد می‌شود |

زمان‌ها بر حسب ثانیه Unix هستند و در این پروفایل باید عدد صحیح باشند. اختلاف ساعت مجاز تعریف نشده است؛ ساعت میزبان باید صحیح باشد. secret فقط در محیط اجرای پروکسی/ابزار صدور وجود دارد و داخل سورس، ایمیج یا گزارش ثبت نمی‌شود. ساخت توکن به معنی ورود کاربر با نام کاربری و رمز نیست؛ در این تمرین مدیر برای کاربر توکن می‌سازد. سرویس صدور توکن عمومی یا سامانه مدیریت کاربران درخواست نشده است.

### راه‌اندازی با Docker Compose

پیش‌نیاز: Docker Engine یا Docker Desktop همراه Compose v2، Python 3 برای دستور تولید secret و آزاد بودن پورت ۸۰. دستورها را در Bash، Linux، macOS یا WSL و از ریشه پروژه اجرا می‌کنیم.

۱. کلید تصادفی ایجاد می‌کنیم. این دستور مقدار secret را در ترمینال چاپ نمی‌کند:

```bash
python3 -c 'import pathlib,secrets; pathlib.Path(".env").write_text("JWT_SECRET="+secrets.token_hex(32)+"\n")'
chmod 600 .env
```

این دستور را برای راه‌اندازی اولیه اجرا می‌کنیم؛ اجرای مجدد آن کلید را عوض کرده و توکن‌های قبلی را بی‌اعتبار می‌کند. فایل `.env` را commit نمی‌کنیم.

۲. کانتینرها را می‌سازیم و اجرا می‌کنیم:

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

`depends_on` ترتیب شروع را مشخص می‌کند و آماده بودن legacy را تضمین نمی‌کند. اگر در چند لحظه نخست پاسخ ۵۰۲ دریافت شد، پس از آماده شدن سرویس دوباره درخواست را می‌فرستیم. برای بررسی خطا:

```bash
docker compose logs --tail=50 proxy legacy
```

۳. بدون توکن درخواست می‌فرستیم:

```bash
curl -i http://localhost/get
```

انتظار: `401 Unauthorized`. هیچ درخواست معتبری به legacy فرستاده نمی‌شود.

۴. توکن پانزده‌دقیقه‌ای تولید می‌کنیم:

```bash
TOKEN=$(docker compose exec -T proxy python generate_token.py --subject student --seconds 900)
```

توکن فقط در متغیر محلی shell نگهداری می‌شود. ابزار داخل کانتینر همان secret و issuer و audience پروکسی را می‌خواند.

۵. درخواست معتبر و درخواست POST می‌فرستیم:

```bash
curl -i -H "Authorization: Bearer $TOKEN" 'http://localhost/get?course=internet'
curl -i -X POST http://localhost/post \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"message":"hello"}'
curl -i -H 'Authorization: Bearer invalid-token' http://localhost/get
```

انتظار: دو درخواست اول پاسخ ۲۰۰ و داده بازتاب‌شده go-httpbin، و درخواست سوم پاسخ ۴۰۱. در خروجی `/get` نباید هدر Authorization وجود داشته باشد.

۶. آزمون خودکار نهایی را روی کانتینرهای در حال اجرا انجام می‌دهیم:

```bash
python3 smoke_test.py
```

این اسکریپت توکن مفقود، خراب، منقضی و با امضای دستکاری‌شده، GET و query تکراری، JSON POST، حذف Authorization، حفظ status، redirect، HEAD و منتشر نشدن پورت legacy را بررسی می‌کند. در صورت شکست هر مورد، با خطا خارج می‌شود. اجرای آن به کانتینرهای واقعی نیاز دارد.

۷. وضعیت عدم انتشار پورت legacy را بررسی می‌کنیم:

```bash
docker compose port legacy 8081
```

نباید نگاشت میزبان نمایش داده شود. خروجی `docker compose ps` ممکن است `8081/tcp` را نشان دهد؛ این با `0.0.0.0:8081->8081/tcp` متفاوت است و به معنی انتشار پورت نیست. تلاش اتصال به `localhost:8081` در نبود سرویس دیگری روی آن پورت، نباید به legacy برسد.

برای توقف:

```bash
docker compose down
```

### اجرای آزمون‌های محلی بدون Docker

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

آزمون‌ها سرور HTTP محلی آزمایشی ایجاد می‌کنند و ارتباط واقعی HTTP از طریق پروکسی را بررسی می‌کنند. این سرور جایگزین کانتینر go-httpbin در آزمون نهایی نیست.

### نتایج ارزیابی انجام‌شده

در محیط آماده‌سازی، ۱۱ آزمون محلی با Python 3.12 و aiohttp 3.14.4 با موفقیت اجرا شدند؛ خروجی خام در `TEST_RESULTS.txt` آمده است. موارد بررسی‌شده شامل رد توکن نامعتبر بدون رسیدن به backend، claimها و امضای JWT، متدها و بدنه، مسیر encode‌شده، جلوگیری از جعل هدر، redirect، status، چند هدر Set-Cookie، عدم اشتراک cookie بین کاربران، پاسخ gzip، سقف حجم و خطای اتصال مقصد است.

در این محیط Docker نصب نبود؛ بنابراین build ایمیج، شبکه Docker و اجرای انتهابه‌انتها روی کانتینر واقعی go-httpbin انجام نشده است. اسکریپت `smoke_test.py` برای اجرای این بررسی روی سیستم دارای Docker ارائه شده است. پاسخ‌های بخش نمونه اجرا، خروجی مورد انتظارند و به عنوان نتیجه مشاهده‌شده Docker گزارش نشده‌اند.

احراز هویت در لبه شبکه اضافه شده و سرویس legacy بدون تغییر کد، پشت پروکسی باقی می‌ماند. محدود کردن دسترسی مستقیم به سرویس مانع دور زدن پروکسی می‌شود و بررسی امضا، زمان و گیرنده JWT تعیین می‌کند کدام درخواست اجازه عبور دارد. TLS مکمل این طراحی برای محافظت از مسیر انتقال است.
